# راه‌اندازی روی سرور شرکت (دیتابیس مشترک PostgreSQL + اکتیودایرکتوری)

هدف: همه‌ی کارشناسان روی **یک دیتابیس واحد** کار کنند و با **اکانت دامنه‌ی خودشان** وارد شوند.

---

## ۱) چه سروری لازم است؟

برنامه یک اپلیکیشن دسکتاپ ویندوزی است؛ پس سرور فقط نقش **نگهدارنده‌ی دیتابیس** را دارد.

| مورد | پیشنهاد |
|---|---|
| سیستم‌عامل | Windows Server 2019/2022 یا یک VM لینوکسی (Ubuntu Server) — عضو یا قابل‌دسترس از دامنه |
| دیتابیس | **PostgreSQL 16** (رایگان و اوپن‌سورس) |
| CPU / RAM | ۲ تا ۴ هسته، ۸ گیگ رم |
| دیسک | ۵۰ گیگ (دیتابیس این برنامه در سال به چند ده مگابایت هم نمی‌رسد) |
| بکاپ | `pg_dump` روزانه‌ی خودکار + کپی روی شیر شبکه |

> **توصیه نمی‌شود** دیتابیس را روی یک شیر شبکه (`\\server\share\database.sqlite`) بگذارید؛ SQLite روی شبکه با چند کاربر همزمان خراب می‌شود. برای کار اشتراکی حتماً PostgreSQL.

---

## ۲) نصب PostgreSQL روی سرور

1. نصب PostgreSQL 16 (روی ویندوز از installer رسمی، روی اوبونتو `apt install postgresql`).
2. ساخت دیتابیس و کاربر برنامه:

```sql
CREATE USER itapp WITH PASSWORD 'یک-رمز-قوی';
CREATE DATABASE itservicelog OWNER itapp;
```

3. اجازه‌ی اتصال از شبکه‌ی داخلی:
   - در `postgresql.conf`:  `listen_addresses = '*'`
   - در `pg_hba.conf` یک خط برای رنج شبکه‌ی شرکت (مثلاً `10.0.0.0/8`) با متد `scram-sha-256` اضافه کنید.
   - سرویس PostgreSQL را restart کنید.
4. پورت **5432/TCP** را در فایروال برای شبکه‌ی داخلی باز کنید.

> کتابخانه‌ی اتصال (`psycopg2`) داخل نسخه‌ی نصبی برنامه بسته‌بندی شده است؛ روی کلاینت‌ها **نیازی به نصب چیز اضافه‌ای نیست**.

---

## ۳) پیکربندی برنامه روی کلاینت‌ها

کنار فایل اجرایی (`C:\Program Files\ITServiceLog\`) فایل `config.json` بسازید:

```json
{
  "db_url": "postgresql+psycopg2://itapp:PASSWORD@SRV-DB:5432/itservicelog",
  "ad": {
    "enabled": true,
    "domain": "company.local",
    "auto_create_users": true,
    "default_role": "Technician",
    "default_department": "IT"
  }
}
```

`SRV-DB` را با نام یا IP سرور دیتابیس و `PASSWORD` را با رمز کاربر `itapp` جایگزین کنید. نمونه‌ی آماده در `config.example.json` کنار همین برنامه هست.

**مسیرهایی که برنامه دنبال این فایل می‌گردد (به ترتیب):**
1. مسیر متغیر محیطی `ITSERVICELOG_CONFIG`
2. کنار فایل اجرایی → `config.json`
3. `%PROGRAMDATA%\ITServiceLog\config.json`  ← **بهترین گزینه برای توزیع با Group Policy**
4. کنار سورس پروژه

می‌توانید به‌جای فایل، فقط متغیر محیطی `ITSERVICELOG_DB` را با آدرس اتصال ست کنید.

اگر هیچ‌کدام نباشد، برنامه دقیقاً مثل قبل روی SQLite محلی کار می‌کند — پس نصب‌های تک‌کاربره‌ی فعلی بدون تغییر ادامه می‌دهند.

> جدول‌ها بار اول به‌صورت خودکار ساخته می‌شوند (کاربر `itapp` چون owner دیتابیس است این دسترسی را دارد). برنامه هنگام هر بار بالا آمدن، ستون‌های جدید نسخه‌ها را هم خودکار اضافه می‌کند؛ پس آپدیت‌ها بدون از دست رفتن داده انجام می‌شوند.

---

## ۴) ورود با اکتیودایرکتوری

با `"ad": { "enabled": true }`:

- کاربر **نام کاربری و رمز ویندوز خودش** را در صفحه‌ی ورود می‌زند (فرمت‌های `user`، `COMPANY\user` و `user@company.local` هر سه قبول است).
- اعتبارسنجی با `LogonUser` ویندوز انجام می‌شود (روی سیستم غیرویندوزی، اگر `ldap3` نصب باشد از LDAP استفاده می‌کند). **رمز عبور هیچ‌جا در برنامه ذخیره نمی‌شود.**
- اگر کاربر اولین بار وارد شود و `auto_create_users` روشن باشد، رکوردش خودکار ساخته می‌شود؛ بعد مدیر در تب «مدیریت کاربران» **نقش** و **بخش** (IT / سایت / هر دو) را برایش تنظیم می‌کند.
- حساب `admin` محلی همچنان کار می‌کند (به‌عنوان راه ورود اضطراری وقتی دامنه در دسترس نیست). **رمز پیش‌فرض `admin` را حتماً عوض کنید.**

---

## ۵) انتقال داده‌های فعلی به سرور

داده‌های موجود در `%APPDATA%\ITServiceLog\database.sqlite` است. برای انتقال به PostgreSQL:

1. برنامه را یک‌بار با `config.json` اجرا کنید تا جدول‌های خالی روی PostgreSQL ساخته شوند.
2. با ابزار **pgloader** (`pgloader sqlite_file postgres_url`) یا DBeaver، جدول‌ها را از فایل SQLite به PostgreSQL کپی کنید — به ترتیب:
   `technicians` → `systems` → `employees` → `tasks` → `service_records` → `service_record_tasks`
3. بعد از انتقال، مقدار sequence هر جدول را sync کنید، مثلاً:
   ```sql
   SELECT setval('tasks_id_seq', (SELECT MAX(id) FROM tasks));
   ```
   (برای هر جدولی که ستون id دارد.)

## ۶) چک‌لیست نهایی

- [ ] PostgreSQL نصب، دیتابیس و کاربر `itapp` ساخته شده
- [ ] `listen_addresses` و `pg_hba.conf` برای شبکه‌ی داخلی تنظیم، پورت ۵۴۳۲ در فایروال باز
- [ ] `config.json` روی کلاینت‌ها (ترجیحاً از طریق GPO در `%PROGRAMDATA%`)
- [ ] بکاپ روزانه‌ی `pg_dump` فعال است
- [ ] رمز حساب `admin` عوض شده است
- [ ] بخش هر کاربر (IT / سایت / هر دو) در «مدیریت کاربران» تنظیم شده است

## ۷) به‌روزرسانی به نسخه‌ی 1.6

نسخه‌ی 1.6 یک ستون جدید به جدول `technicians` (`can_log_key_activities`) و دو جدول جدید
(`key_activities`, `key_activity_updates`) اضافه می‌کند. جدول‌های جدید خودشان در اولین
اجرا ساخته می‌شوند، اما اضافه‌کردن ستون به جدول موجود روی PostgreSQL نیازمند قفل
ACCESS EXCLUSIVE است؛ اگر همان لحظه کلاینت‌های دیگری از نسخه‌ی قبلی باز باشند و
تراکنشِ نیمه‌باز (idle in transaction) روی `technicians` داشته باشند، این قفل صف
می‌کشد و هر پرس‌وجوی بعدی روی آن جدول هم پشتِ صف می‌ماند — یعنی کل شرکت فریز می‌شود.

برای همین، برنامه هنگام این migration یک `lock_timeout` کوتاه (۵ ثانیه) می‌گذارد؛
اگر قفل گرفته نشود، به‌جای فریز شدن، فقط همان کلاینت با پیام روشن «برنامه روی
سیستم‌های دیگر باز است» متوقف می‌شود.

**قبل از اولین اجرای نسخه‌ی 1.6:**

- همه‌ی کپی‌های باز برنامه (روی همه‌ی کلاینت‌ها) را ببندید و بعد یکی را اجرا کنید، **یا**
- پیش‌تر، یک‌بار به‌عنوان مالکِ دیتابیس این SQL را روی PostgreSQL اجرا کنید:

```sql
SET lock_timeout = '5s';
ALTER TABLE technicians ADD COLUMN can_log_key_activities BOOLEAN;
UPDATE technicians SET can_log_key_activities = FALSE WHERE can_log_key_activities IS NULL;
```

- جدول‌های جدید (`key_activities`, `key_activity_updates`) نیازی به این کار ندارند؛ چون
  جدول تازه‌اند (نه ستونِ اضافه‌شده به جدول موجود)، در اولین اجرا خودکار ساخته می‌شوند.
- اگر این SQL هم به‌خاطر قفل ACCESS EXCLUSIVE با خطای timeout شکست خورد، کلاینت‌های باز را
  ببندید و دوباره اجرایش کنید.
- اگر یک کلاینت هنگام بالا آمدن پیغام «همه‌ی نسخه‌های باز برنامه را ببندید و دوباره اجرا
  کنید» را دید، بقیه‌ی کپی‌های باز را ببندید و دوباره اجرا کنید.

**دسترسی به تبِ «کارهای شاخص IT» پس از نصب:** مدیرها (Administrator) بدون هیچ تنظیمی این
تب را دارند. برای کاربرِ دیگری (مثلاً مدیر واحد که نقشش «کارشناس» است) در «مدیریت کاربران IT»
تیک «ثبت کارهای شاخص» را بزنید؛ از ورود بعدیِ آن کاربر فعال می‌شود. این قاعده فقط در کد
است و به تغییر دیگری در دیتابیس نیاز ندارد.

## گزینه‌ی جایگزین: SQL Server

اگر شرکت از قبل SQL Server دارد، همین برنامه با آن هم کار می‌کند — فقط `db_url` را
عوض کنید و روی کلاینت‌ها **ODBC Driver 17/18 for SQL Server** نصب باشد:

```
mssql+pyodbc://@SRV-DB\SQLEXPRESS/ITServiceLog?driver=ODBC+Driver+17+for+SQL+Server&trusted_connection=yes
```

> برای بسته‌بندی پشتیبانی SQL Server در نسخه‌ی نصبی، پیش از `build.ps1` باید در محیط build دستور `pip install pyodbc` را هم زده باشید. (پشتیبانی PostgreSQL به‌صورت پیش‌فرض بسته‌بندی می‌شود.)

## ۸) بکاپ روزانه‌ی خودکار (از نسخه‌ی 1.6.4)

برنامه‌ی نصب‌شده با پارامتر `--backup` بدون باز کردن پنجره، از دیتابیس PostgreSQL سرور یک
فایل SQL (مثل خروجی متنی `pg_dump`) می‌سازد — مثلاً `ITServiceLog_1405-07-15.sql` — و فقط
۳ بکاپ آخر را نگه می‌دارد. به نصب pg_dump روی سیستم نیازی نیست.

```
"C:\Program Files\ITServiceLog\ITServiceLog.exe" --backup "D:\Backups\ITServiceLog" --keep 3
```

- ثبت در Task Scheduler (هر روز ساعت ۱۳، و اگر سیستم خاموش بود به‌محض روشن شدن):
  `powershell -ExecutionPolicy Bypass -File scripts\setup_backup_task.ps1`
- نتیجه‌ی هر اجرا در `backup.log` همان پوشه نوشته می‌شود.
- بکاپ جدید اول کامل و بررسی می‌شود؛ تا موفق نشده، هیچ بکاپ قبلی پاک نمی‌شود.
- فایل بکاپ شامل ساخت جدول‌ها + همه‌ی داده‌ها + تنظیم sequence هاست، داخل یک تراکنش.

**برگرداندن بکاپ** (همیشه روی یک دیتابیس **خالی**؛ دیتابیس فعلی دست نمی‌خورد):

```sql
CREATE DATABASE itservicelog_restore OWNER itapp;
```

```
psql -h 10.0.13.12 -U itapp -d itservicelog_restore -f ITServiceLog_1405-07-15.sql
```

یا از سیستمی که psql ندارد:
`python scripts\restore_backup.py <فایل بکاپ> --target "postgresql+psycopg2://itapp:PASSWORD@10.0.13.12:5432/itservicelog_restore"`

بعد از بررسی، `db_url` را به دیتابیس جدید عوض کنید (یا نام دو دیتابیس را جابه‌جا کنید).

## ۹) به‌روزرسانی از داخل برنامه (از نسخه‌ی 1.6.6)

دیگر لازم نیست فایل نصبی را دستی روی سیستم‌ها ببرید. فایل نصبیِ هر نسخه در جدول
`app_releases` همان دیتابیس سرور قرار می‌گیرد و برنامه‌ی کاربران خودش اعلان می‌دهد:

1. تغییرات را بدهید و `build.bat` را اجرا کنید (فایل `release\ITServiceLog-Setup-<نسخه>.exe` ساخته می‌شود).
2. `publish.bat` را اجرا کنید و توضیح کوتاه تغییرات را بنویسید.
3. هر کاربر در اولین اجرای برنامه، یا اگر برنامه باز است حداکثر تا ۲ ساعت بعد، پیام
   «نسخه‌ی جدید آماده است» را می‌بیند. با «به‌روزرسانی» فایل دانلود و بررسی (sha256) می‌شود،
   برنامه بسته می‌شود، نصب انجام می‌شود و برنامه دوباره باز می‌شود. «بعداً» تا اجرای بعدی دیگر نمی‌پرسد.

نکته‌ها:
- چون برنامه در `Program Files` نصب است، ویندوز هنگام نصب اجازه‌ی مدیر (UAC) می‌خواهد. کاربری که
  ادمین سیستم خودش نیست، باید رمز ادمین وارد شود.
- سیستم‌هایی که نسخه‌ی قدیمی‌تر از 1.6.6 دارند، **یک بار آخر** باید دستی نصب شوند؛ از آن به بعد خودکار است.
- فایل نصبی فقط داخل شبکه (روی دیتابیس) است و جایی عمومی منتشر نمی‌شود — مهم است، چون آدرس و رمز
  دیتابیس داخل `config.json` همین فایل نصبی است.
- فقط فایل دو نسخه‌ی آخر در دیتابیس نگه داشته می‌شود و این جدول در بکاپ روزانه نیست.
